# ex-co-model 设计文档

日期：2026-08-25
状态：待评审

## 1. 产品定位

一个由 AI 驱动、供游戏开发者使用的 3D 建模工具。人作为创作者/美术指导，只通过**文字 + 图片**（含预览视口上的圈选标注）输入意图；AI 作为"建模工"执行具体建模操作。

核心差异化：不输出"烘焙死"的生成网格，而是输出**可编辑的结构化建模描述**——每次修改只动局部，可回退、可调参，而不是推倒重生成。

首发用户：独立游戏开发者（第一用户是作者自己的游戏项目，dogfooding 驱动）。

## 2. 已确认的关键决策

| 决策点 | 结论 |
|---|---|
| 投入程度 | 认真做产品，非玩具/demo |
| 第一批用户 | 游戏开发者（独立游戏/Mod 作者） |
| 本地化策略 | 混合架构：生成模型与数据在本地，规划/推理允许云端 LLM，质量优先 |
| 第一版资产范围 | 只做静态资产（道具/建筑/舰船），不做角色与骨骼蒙皮 |
| 技术路线 | 操作树（OpTree）+ Blender headless 内核 + 精模部件库 |
| 精度策略 | 精度来自参数化与确定性几何操作，不来自生成模型 |
| 工作流定位 | "人指挥、AI 执行"，非"一句话出成品" |
| 自用与产品化 | 自用先行（自己的游戏项目验证），产品化后置 |

## 3. 核心抽象：OpTree（操作树）

每个资产是一份可执行的 JSON 描述（DAG）。铁律：**LLM 只读写 OpTree，永远不直接操作 mesh**——它操作几十行 JSON，而不是几十万个顶点。这是可编辑性与 AI 可靠性的共同来源。

确定性规则：每个节点同参数同输入必同输出。修改一个节点只需重算其下游子树，实现增量更新。

### 节点分类（v1）

- **Source**：`primitive`（参数化基础体：box/cylinder/hull-loft 等）、`attach_part`（精模部件库）、`import`（外部 mesh；语义分割归 v2）、`generate_organic`（生成模型，仅有机形状，可选）
- **Construct**（精度核心）：`extrude`、`inset`、`bevel`、`boolean_union`、`boolean_subtract`、`mirror`、`array`、`loft`、`decimate`（兼作 LOD 派生）
- **有机形状附加节点**（仅 `generate_organic` 路径）：`retopo`、`uv_unwrap`、`bake_texture`
- **Transform**：`scale_to`（含物理单位换算）、`align`、`snap`
- **Material**：`assign_shader`（程序化着色器）、`apply_trim`（trim sheet）、`assign_material_slot`
- **Export**：`export_fbx`（引擎单位、LOD 由 `decimate` 派生）

## 4. 整体架构（四进程）

1. **UI 壳**（Tauri/Electron，很薄）：预览视口 + 指令输入 + 圈选标注 + OpTree 只读展示
2. **编排服务**（本地 Python）：自然语言 → 云端 LLM → OpTree 结构化修改（JSON diff）→ 校验 → 调度执行 → 增量重算
3. **内核 worker**（Blender headless 子进程）：执行 OpTree 节点，每节点对应一组 `bpy` 调用
4. **生成 worker**（本地 GPU）：TRELLIS/Hunyuan3D 推理，仅被 `generate_organic` 调用，可选组件

### 数据流示例（"在 Razorback 三条腿中间加 PDC 武器槽"）

1. 用户输入指令 + 参考图，可在预览上圈选大致位置
2. 云端 LLM/VLM 读取当前 OpTree + 渲染图定位，输出 OpTree diff（新增 `boolean_subtract` 开槽节点 + `attach_part("pdc_turret", mount=slot)`）
3. 编排服务做 schema 校验与几何预检（布尔目标存在、参数在域内）
4. Blender headless 重算受影响子树，刷新预览
5. **AI 自检闭环**：VLM 对比渲染结果与意图描述，不合格则自动让 LLM 再改一轮；超过 N 轮才把问题呈现给用户

### 部件库

第一批按自有游戏风格制作 10–20 件精模：PDC、引擎喷口、天线、舱门、散热器等，每件带挂载点定义（snap 接口）。部件库同时承担风格统一职责——整个游戏资产共享同一套 kit。**MVP 阶段部件只从库选，不做生成式新部件**（用自由度换可靠性与局部精度）。

## 5. 精度预期管理（诚实边界）

| 资产类型 | 能达到的水平 |
|---|---|
| 背景道具、远景建筑、填充资产 | 可商用，独立游戏直接用 |
| 中景功能资产（武器、载具部件、自有舰船） | 目标：可用精度，参数化构建 + 精模部件装配 |
| 英雄资产（特写镜头级） | 不承诺，AI 建模工 + 人工精修兜底 |

精度来源排序：参数化 Construct 操作（数学精确）> 精模部件库 > 程序化材质/trim sheet > 生成模型（仅有机大形）。

## 6. MVP 范围

### 做

- 资产创建入口：`primitive` 构建为主；`text_to_3d`/`image_to_3d` 仅用于有机形状
- OpTree v1 节点（约 15 种以内，见第 3 节）
- 编辑能力三类：参数修改（缩放/面数等确定性操作）、布尔开槽挖洞、部件拆装
- 预设部件库 10–20 件
- FBX 导出（正确单位/材质/面数，Unity/Unreal 通吃；引擎插件归 v1.1）
- UI 壳：预览 + 指令框 + 圈选 + OpTree 只读展示
- AI 自检闭环（VLM 渲染对比）

### 不做（防 scope creep）

- 角色资产 / 骨骼蒙皮
- 外部模型导入后的语义部件分割（v2）
- 生成式新部件（v2）
- 多物件场景（MVP 一次一个资产）
- 纯本地 LLM 模式
- 引擎插件、OpTree 可视化编辑（v1.1）

### 验收标准

用本工具做出自有游戏真实需要的一艘舰船，达到愿意放进游戏的精度。自有游戏的资产清单即端到端测试集。

## 7. 错误处理原则

- LLM 的所有 OpTree 修改先过 schema 校验 + 几何预检，不合法则把结构化错误信息回喂重试
- 重试超过 N 轮后，将失败原因呈现给用户，请其换种表述
- **AI 的失败永远不能呈现为坏模型，只能呈现为"我没做到，请换种说法"**

## 8. 测试策略

- OpTree 执行器是纯函数式：每个节点独立单测（同输入同输出断言）
- 编排服务：OpTree diff 的 schema 校验与几何预检单测
- 端到端回归集：自有游戏的真实资产清单（"造一艘 X 级护卫舰"跑通并达标为准入）

## 9. 主要风险

| 风险 | 缓解 |
|---|---|
| LLM 空间规划能力不足，复杂造型协调性差 | 人指挥 AI 执行的分工；AI 自检闭环；模糊位置用圈选兜底 |
| 生成模型硬表面质量差 | 已降级为可选组件，精度走参数化路线 |
| 部件库制作成本高 | 首批只做 10–20 件，与游戏资产需求复用 |
| 大厂下场同质竞争 | 护城河在 OpTree 工具链质量 + 游戏资产工作流集成深度 |
